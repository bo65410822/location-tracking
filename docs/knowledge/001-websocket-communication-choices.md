# 知识点:WebSocket 通信选型(原生 vs STOMP、JSON vs 二进制)

## 1. 要解决什么问题

本项目已决定三端统一用 WebSocket 做实时通信(见 #决策002)。但"用 WebSocket"还剩两个"怎么用"的问题要定:

- **编程模型**:用 WebSocket 的哪种用法——原生 handler,还是 STOMP 消息代理?
- **消息格式**:消息体用什么装——JSON 文本,还是自研二进制帧?

这两个选错了,后面 App、Server、Web 三端都要返工,所以先讲清楚再定。

## 2. 核心概念

- **WebSocket**:在**单条 TCP 连接**上做**全双工**通信的协议。先用一次 HTTP 请求"握手升级"(响应码 `101 Switching Protocols`),之后这条连接就一直开着,双方都能随时主动发消息(帧)。对比传统 HTTP:HTTP 是"一问一答、答完即断",服务端无法主动推;WebSocket 建好后服务端可以主动把数据推给客户端——这正是实时定位看板需要的。

- **原生 WebSocket**(Spring 里的 `TextWebSocketHandler` / `WebSocketHandler`):你直接拿到每一条收到的消息(文本或二进制),自己解析内容、自己管理每个连接(`WebSocketSession`)。最贴近协议本身,"收发什么、怎么解析"全由你定。

- **STOMP**:一个**架在 WebSocket 之上的"消息语义层"**文本协议,带 `CONNECT/SUBSCRIBE/SEND/MESSAGE` 等命令。配合 Spring 的消息代理,可以实现"客户端订阅某个主题 `/topic/xxx`、服务端往主题发消息、框架自动广播给所有订阅者"。相当于在 WebSocket 上套了一个轻量级的消息队列(发布/订阅)模型。

## 3. 可选方案对比

### 维度一:编程模型 —— 原生 WebSocket vs STOMP

#### 方案 A:原生 WebSocket
- 优点:
  - 概念简单、贴近协议,对正在补后端的你学习曲线友好。
  - **App(Android 原生)实现成本低**:用 OkHttp 的 WebSocket 直接收发 JSON 即可,不需要在客户端实现一套 STOMP 协议栈。
  - 消息格式完全自定义,三端用同一套 JSON,心智一致。
- 缺点:
  - 主题订阅、点对点路由要自己写(但切片1 只有"上报 + 全量广播",用不到)。
  - 心跳、断线重连、超时要在应用层自己封装(不过这本来就是我们想亲自掌控的点)。

#### 方案 B:STOMP over WebSocket
- 优点:
  - 自带主题订阅/广播模型(`@MessageMapping` + `/topic/**`),多频道、多房间场景很省事。
  - 浏览器端有成熟库(stomp.js),Spring 集成度高。
- 缺点:
  - **对 Android 原生客户端是额外负担**:要额外引入/实现 STOMP 协议,成本实打实。
  - 多出"目的地 / 消息代理 / 帧命令"等一层抽象,初学者心智负担大。
  - 对我们"自定义 JSON + 三端一致 + 最小闭环"的目标属于**过度设计**。

**→ 选 A(原生)**:切片1 只有"上报"和"广播"两种数据流,STOMP 的订阅能力没有收益,而它对 App 端的成本却是真实存在的。

### 维度二:消息格式 —— JSON 文本 vs 自研二进制帧

#### 方案 A:JSON 文本
- 优点:
  - Web 端原生解析(`JSON.parse`),三端都友好。
  - 可读、可调试、易演进(加字段天然向后兼容)。
  - 开发成本低,不用管字节序/粘包(WebSocket 已经分好帧)。
- 缺点:
  - 体积比二进制大(单个定位点约 150–250B,二进制约 30–50B)。
  - 文本解析有一定 CPU 开销(数据量极大时才显著)。

#### 方案 B:自研二进制帧
- 优点:
  - 体积小、省流量,可做极致的协议控制。
- 缺点:
  - Web 端要手写 `DataView` 逐字节解析,痛苦且易错。
  - 可读性差、排障难,演进要同步管字节序与版本。
  - 维护成本高。

**→ 选 JSON**:定位点体积小、上报频率秒级,二进制省下的几十字节,相对 GPS 持续采集与射频唤醒的能耗、以及现代移动带宽,只是零头;可读性与开发效率的价值更高。(完整论证见 ADR 002)

## 4. 本项目的选择与理由

**原生 WebSocket + JSON**。既满足三端统一(#决策002),又让 App 端成本最低、Web 端最友好,契合切片1 最小闭环(#决策005)。心跳/重连/超时这些由应用层自己封装,反而让我们对弱网/后台行为有更精细的掌控。

## 5. 已知约束 / 风险 / 延伸

- 心跳、重连、超时、断线会话恢复需在**应用层自己实现**——这是原生模型的"代价",但也是我们主动要的掌控点。
- 服务端 Web 广播若用**单机内存会话集合**,一旦多实例部署,A 实例收到的上报广播不到连在 B 实例上的 Web 客户端。切片1 单机可接受,集群时需引入 **Redis Pub/Sub 或消息队列**(列入 backlog)。
- 延伸学习:WebSocket 握手与帧结构(RFC 6455)、`permessage-deflate` 压缩、SockJS 回退机制、STOMP 真正适用的场景(聊天室/多人协作这类强订阅模型)。
