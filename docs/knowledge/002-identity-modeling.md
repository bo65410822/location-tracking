# 知识点:身份建模 —— 设备身份 vs 主体身份,以及用中性标识解耦

## 1. 要解决什么问题

定位系统要回答"**这条位置是谁的**"。最直觉的做法是用 `deviceId`(设备号)当身份,但这会把"**人/被追踪的主体**"等同于"**手机/设备**"。一旦换手机、重装、恢复出厂,设备标识变了,系统就当成另一个对象,**历史轨迹断裂**。本卡片讲清身份该怎么建模。

## 2. 核心概念

身份其实有两层,别混为一谈:

- **设备身份(device identity)**:标识"**哪台设备**在上报"。随换机/重装/恢复出厂而变。
- **主体身份(subject identity)**:标识"**被追踪的人/物是谁**",应当**跨设备稳定**(张三换了手机还是张三)。

补充:**设备层面没有完美的永久标识**——
- Android ID(SSAID):恢复出厂、换 App 签名会变。
- 本地自生成 UUID:卸载重装就丢。
- IMEI/硬件标识:新版系统拿不到权限、隐私受限,不推荐。

→ 这正是"需要一个与设备解耦的、服务端/账号体系维护的主体 ID"的根本原因。

## 3. 可选方案对比

### 方案 A:直接用 deviceId 当身份
- 优点:实现最简单,App 本地就能产生。
- 缺点:把"人"绑死到"设备";换手机轨迹断裂;协议/表结构被"设备"语义绑死,日后升级要改动。

### 方案 B:切片1 就引入完整 subject/user + 设备绑定模型
- 优点:身份建模一步到位,不返工。
- 缺点:需要账号注册、设备绑定、鉴权,严重超出最小闭环(#决策005),拖慢主线。

### 方案 C(本项目采用):用语义中性的 `sourceId` 解耦
- 做法:协议里只放一个**不透明字符串** `sourceId`,**服务端不解释语义**;填设备号/用户号/车辆号由**上层决定**;Web 按相同 `sourceId` 归并轨迹。
- 优点:
  - 协议与表结构**稳定**,身份语义怎么变都不改协议。
  - **关注点分离**:语义是上层的事,传输层只"按值分流 + 存 + 广播"。
  - **平滑演进**:切片1 填设备级值,鉴权切片填主体值,零协议改动。
- 缺点 / 注意:
  - 服务端**不理解语义**,无法在服务端做身份级业务校验(切片1 不需要)。
  - 值的**唯一性/稳定性责任转移到上层**;上层填了会变的值,轨迹照样断——但这是接入方的使用问题,架构层不背锅。
  - 若将来**既要设备又要主体**两个维度,`sourceId` 单值不够,需**再加一个字段**(JSON 向后兼容,不破坏现有协议)。

## 4. 本项目的选择与理由

采用**方案 C**:身份字段用中性的 `sourceId`。既避免了方案 A"设备绑死"的坑,又不像方案 B 那样把账号体系提前拉进切片1。真正的"主体身份跨设备稳定"留到鉴权切片用账号/设备绑定解决。

## 5. 已知约束 / 风险 / 延伸

- 切片1 的 `sourceId` 本质还是设备级值,**换手机轨迹会断**——这是**已知局限**,非架构缺陷,待鉴权切片引入主体身份后消除。
- 延伸学习:账号—设备 一对多绑定建模、设备指纹的稳定性与隐私合规、匿名标识与可追踪性的权衡。
