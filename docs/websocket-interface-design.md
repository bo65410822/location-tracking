# 切片1 WebSocket 接口设计

> 范围:切片1 服务端 WebSocket 接口(App 上报 + Web 实时广播)。
> 选型依据见 #决策002(三端统一 WebSocket + JSON)与知识卡片 `knowledge/001`。
> 本文定义"接口长什么样",不含实现代码(代码由主力开发完成)。

## 1. 目标与数据流

切片1 要打通的闭环:

```
App ──(JSON 定位点)──> /ws/app ──> 存库(JPA/H2) ──> 广播 ──> /ws/web ──> Web 实时列表
```

- App 通过 WebSocket 持续上报定位点。
- 服务端收到后落库,并实时广播给所有在线的 Web 看板。
- Web 端只做坐标列表展示(地图后置,#决策005)。

## 2. 端点设计

按角色分两个端点,职责隔离:

- `/ws/app` —— App **上报**定位点(上行为主)。
- `/ws/web` —— Web 看板**接收**实时推送(下行为主)。

**为什么分两个端点(而非单端点按消息角色区分):**
- 优点:上/下行职责清晰;后续加鉴权、限流、监控可对两端分别施策(App 端要设备鉴权,Web 端要用户鉴权,策略不同)。
- 代价:多一个 handler。切片1 可接受。

## 3. 消息协议(JSON)

### 3.1 App → Server(上报)

```json
{
  "type": "location",
  "sourceId": "src-001",
  "lat": 39.9042,
  "lng": 116.4074,
  "speed": 1.2,
  "bearing": 90.0,
  "accuracy": 5.0,
  "timestamp": 1760000000000
}
```

字段说明:

- `type`:消息类型。切片1 固定 `"location"`;保留字段,用于后续区分心跳/ack 等。
- `sourceId`:**轨迹来源的中性标识**(不透明字符串)。服务端**不解释其语义**——它可以是设备号、用户号、车辆号等,由**上层(接入方)决定填什么**;Web 端按相同 `sourceId` 把点归为同一条轨迹。切片1 由 App 端填一个设备级的值。**必填**。详见 #决策010 与知识卡片 `knowledge/002`。
- `lat` / `lng`:纬度 / 经度。**原始 WGS84 坐标**,坐标纠偏(→GCJ-02)后置(#决策005)。**必填**。
- `speed`:速度(m/s)。可空。
- `bearing`:方向角(度,0–360)。可空。
- `accuracy`:定位精度(米)。可空。
- `timestamp`:采集时间,Unix 毫秒时间戳。**必填**。

**切片1 暂不加的字段(及原因)**:`altitude`(看板不展示海拔)、`battery`(切片1 不展示电量)。身份语义已用中性的 `sourceId` 解耦(见 #决策010),无需单独的 `userId`——需要区分"设备 vs 主体"时再加一个维度字段即可。`type` + JSON 的组合保证加字段向后兼容。

**关于 `sourceId` 的已知局限**:服务端不校验其唯一性/稳定性,这个责任在上层。若上层填了会变的值(如换手机换了值),轨迹仍会断裂——但这是接入方的使用问题,非架构层问题。真正的"主体身份跨设备稳定"需在鉴权切片引入账号/设备绑定模型后解决。

### 3.2 Server → Web(广播)

在上报对象基础上,附加服务端生成的两个字段:

```json
{
  "type": "location",
  "sourceId": "src-001",
  "lat": 39.9042,
  "lng": 116.4074,
  "speed": 1.2,
  "bearing": 90.0,
  "accuracy": 5.0,
  "timestamp": 1760000000000,
  "id": 1024,
  "serverTime": 1760000000500
}
```

- `id`:落库后的主键,便于 Web 端去重 / 定位记录。
- `serverTime`:服务端接收(落库)时间,Unix 毫秒。便于排序与端上时钟漂移对齐。

### 3.3 心跳(保留约定,切片1 收尾时落地)

- App 定期发 `{"type":"ping"}`,服务端回 `{"type":"pong"}`。
- 用途:检测连接假死,配合 App 端重连(呼应 #决策004)。
- 切片1 可先依赖容器默认超时,心跳的具体间隔/假死判定在切片1 收尾或切片2 落地。

## 4. 处理流程(服务端)

1. App 连接 `/ws/app`,发送 location JSON。
2. 服务端 handler:解析 JSON → 校验必填(`sourceId`/`lat`/`lng`/`timestamp`)→ 落库(`LocationPoint`,JPA)→ 构造广播消息(补 `id`/`serverTime`)→ 推送给所有 `/ws/web` 会话。
3. Web 收到后追加到列表渲染。

## 5. 广播模型

- 服务端维护一个**线程安全的 Web 会话集合**(如 `CopyOnWriteArraySet<WebSocketSession>`)。
- Web 连接建立(`afterConnectionEstablished`)时加入,关闭(`afterConnectionClosed`)时移除。
- 收到上报即遍历集合扇出(fan-out)。
- App 连接不加入该集合(App 只上报,不接收广播)。

**已知约束(重要):**

- **单机内存广播**:会话集合在单个 JVM 内。一旦服务端多实例部署,A 实例收到的上报**广播不到**连在 B 实例上的 Web 客户端。
  - 切片1 单机运行 → 可接受。
  - 集群时的解法:引入 **Redis Pub/Sub** 或消息队列(MQ),各实例订阅同一频道,收到上报后发到频道,所有实例再推给各自本地的 Web 会话。列入后续切片。

- **`WebSocketSession` 非线程安全**:多个 App 并发上报会触发并发广播,若多线程同时向**同一个** Web 会话 `sendMessage`,会抛异常或损坏帧。
  - 解法:用 Spring 的 `ConcurrentWebSocketSessionDecorator` 包装会话,或对单会话发送加锁 / 串行化。
  - 已登记为知识点(见 `knowledge/README.md` backlog)。

## 6. 错误处理(切片1 最小策略)

- JSON 解析失败:记日志,**丢弃该条**,不断开连接。
- 必填字段缺失:记日志,丢弃该条。
- 落库异常:记日志;切片1 **不做重试 / 不入死信**(后续切片再考虑可靠投递)。
- 原则:切片1 以"跑通闭环"为先,容错从简,但不能因单条坏消息拖垮连接。

## 7. 安全约束(必须知悉)

切片1 的 `/ws/app`、`/ws/web` **均无鉴权**——任何人知道地址即可连接、上报或接收数据。按 #决策005 鉴权后置,切片1 本地验证可接受,但这是**已知安全缺口**,上线/多端前**必须**补:App 端设备鉴权、Web 端用户鉴权、连接握手校验 token。
