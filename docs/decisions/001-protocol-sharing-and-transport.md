# ADR 001:协议共享 + 两段式传输

- 状态:已确认(协议抽离部分已实现)
- 日期:2026-10-12

## 背景

新系统需要 App 与服务端通信,并把数据实时推给网页。作者已有一套 Android 长连接实现(Tracelet 的 tracelet-lc),其中帧协议是纯逻辑。核心问题:协议代码如何在 App 与服务端之间保持一致,以及 App↔Server 与 Server↔Web 两段链路各用什么传输。

## 决策

1. **协议抽成独立纯 JVM 库 lc-protocol**,App 与服务端共同依赖,协议只写一遍。
2. **两段式传输**:App↔Server 用 LC 自研 TCP 长连接(二进制帧);Server↔Web 用 WebSocket。协议层只覆盖第一段。

## 理由

- 协议是两端唯一必须字节级一致的部分,各写一份极易产生解析分歧(CRC、字节序、粘包边界),共享库从根上消除。
- 纯 JVM 库使 Java 后端可直接依赖,无需移植。
- App 侧长连接满足省电/实时/弱网可控并复用既有能力;Web 侧 WebSocket 通用、低成本。两段解耦,互不牵制。

## 影响与约束

- 协议类须 public;各端 JVM target 一致(当前 11)。
- 服务端必须直接依赖 lc-protocol(不经 tracelet-lc 传递)。
- 服务端需实现 lc-protocol 的服务端解帧逻辑(复用同一库的编解码)。
- Web 通道可独立演进(换 SSE/轮询)而不影响 App 链路。

## 备选与放弃原因

- App↔Server 也用 WebSocket:省了服务端自研解帧,但丢掉自研协议这一差异化,且对后台保活/弱网控制不如自研长连接精细——放弃。
- 协议各端各写一份:无需建共享模块,但两端一致性全靠人工维护,风险高——放弃。
